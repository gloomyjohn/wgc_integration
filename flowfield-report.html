Algorithm Loop

Flow Field 的完整闭环

无论后端还是 TSX，本质都遵循同一个闭环： 需求点 产生吸引向量， 道路方向 决定向量能否转化为有效引导， 最终得到 路径或运动行为。

统一算法框架

Step 1

从需求侧取输入。后端读取数据库中的未匹配乘客；TSX 从仿真中的 passenger 列表读取活跃需求。

Step 2

在某个空间位置计算乘客吸引向量，距离越近权重越大，并通过 spread 项避免数值过强。

Step 3

把吸引向量投影到道路前进方向上，只保留顺着道路方向的有效引导。

Step 4

根据投影结果做决策。后端调整边代价参与搜索；TSX 直接在路口挑选对齐度最高的下一条边。

Step 5

输出结果。后端输出完整路线 DTO；TSX 输出司机运动、预测路径和矢量场展示。

项目里的两个层级

全局层

后端 `calculateCurrentFlowField()` 会把多个乘客的影响叠加到各条路段上，得到整个路网的需求引导强度。

局部层

后端 `buildRouteToPassenger()` 和 TSX `nearestPassengerField()` 都会在局部位置上重新计算朝向目标的吸引向量。

约束层

两边都不允许脱离道路网络自由移动，向量必须服从已有路段方向。

输出层

后端强调可调用、可返回；TSX 强调可观测、可解释、可视化。

Backend

后端实现: 用 Flow Field 给 A* 加偏置

后端不是直接让车“跟着箭头走”，而是把 flow field 作为 边代价的奖励项， 让图搜索更偏向需求方向，同时保留全局寻路能力。

Backend Flow

调用链

  • `/v1/pathRecommendations/getRec` 接收司机位置和乘客位置。
  • `PathRecommendationsServiceImpl.getRecommendedPath()` 调用 `flowFieldService.buildRouteToPassenger()`。
  • 服务先把司机和乘客吸附到最近路段，再进入 `findRouteSegments()` 做搜索。
  • 最终返回 `FlowFieldRouteResultDTO`，再封装为前端消费的 `bluePath`。
Backend Logic

核心机制

  • 服务启动时缓存全部路段向量和路网邻接表，避免每次查库重建图。
  • `calculateCurrentFlowField()` 会把所有活跃乘客的吸引力叠加到路段中点上。
  • `traversalCost()` 先算基础长度，再根据候选边与局部场方向的一致性降低代价。
  • `findRouteSegments()` 使用 `costSoFar + heuristic`，本质是 A* 风格启发式搜索。

输入侧

乘客数据来自 `ride_requests` 表中的未匹配需求，路网来自 `road_segments`，并使用最近路段吸附把点映射到图上。

决策侧

flow field 不直接决定下一跳，而是通过降低顺向边成本，让搜索结果更容易沿着需求梯度前进。

输出侧

输出是一条完整路线，包括起点吸附、目标吸附、路段序列和折线路径点，更适合真实接口调用。

“

后端的关键不是“算出场”，而是“把场嵌入图搜索”。

这句话可以作为本页总结，强调后端实现不是纯可视化势场，而是工程化路线规划。

Simulator TSX

TSX 实现: 局部 Flow Field 驱动在线贪心导航

`RealtimeTaxiSimulatorProbabilityAware.tsx` 更偏仿真。它在每个路口实时看局部场方向， 直接挑选下一条最对齐的路段，并把整个向量场画出来。

TSX Flow

司机怎么走

  • `nearestPassengerField()` 只取最近乘客，不叠加所有乘客。
  • `moveTaxiFieldBased()` 负责空驶司机沿着道路推进。
  • 当一条边走完后，调用 `chooseNextEdgeFieldAligned()` 在路口选下一条边。
  • 如果局部场很弱，就退化为“偏向直行、惩罚掉头”的随机选择。
TSX Display

为什么适合展示

  • `buildFlowFieldOverlay()` 在边中点取样，生成箭头长度、透明度、粗细随场强变化的矢量图层。
  • `flowFieldEnabled` 可以开关引导逻辑，`showVectorField` 可以开关显示。
  • 场强还能放大空驶速度，形成“需求越强，运动越快”的直观效果。
  • 还包含卡住重生、掉头惩罚、demo path 预测等仿真增强机制。

求解方式

它不维护全局 frontier，也不显式回溯整条最优路径，而是在当前路口局部决策，因此更像在线贪心导航。

数据形式

依赖的是前端内存图结构和像素坐标系，`spreadPx` 也是由实际距离换算为像素尺度之后再参与计算。

输出形式

重点不是 DTO，而是实时 taxi 状态、预测路径、矢量场叠加层和仿真中的可视化行为。

“

TSX 不是把 flow field 当成“搜索偏置”，而是把它当成“下一步 steering 信号”。

这一句适合拿来和后端形成对照，帮助老师快速理解两种实现层次。

为什么后端不能只用 TSX 那套

因为业务接口需要一条完整、稳定、可复现的路径结果，仅靠路口贪心可能会陷入局部最优，缺少全局保证。

为什么汇报时不能把两者当成重复实现

因为它们服务于不同问题。后端解决“怎么返回路线”，TSX 解决“怎么解释车辆为什么这样走”。

开场

项目中的 flow field 逻辑分成后端正式实现和前端仿真实现，两边共享“需求吸引场 + 路网约束”的思想。

后端

后端把乘客需求转成对道路的引导方向，再把这种方向性作为边代价的奖励项，嵌入 A* 风格的路径搜索，所以更偏全局规划。

TSX

TSX 文件则在每个路口实时计算局部 flow field，并直接挑选最对齐的下一条边，同时把向量场画出来，所以更偏局部导航和仿真展示。

收束

因此，后端负责“给出一条可落地的推荐路径”，TSX 负责“解释车辆如何在需求场中运动”，两者不是重复，而是分工互补。

答辩时的高频问题

为什么叫 flow field？

因为先由乘客需求生成空间方向场，再把这个方向场映射到道路网络中用于引导。

为什么后端还要 A*？

因为 flow field 只给方向偏好，完整可用的路径仍然需要全局搜索来保证稳定性。

TSX 为什么只取最近乘客？

因为它更强调局部动态响应和可视化直觉，而不是严格求全局最优。

两边能否统一？

可以在思想上统一，但实现不必完全相同，因为业务接口和仿真展示关注点不同。
